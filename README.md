# Amazon-ML
## Overview

This project implements an end-to-end **entity matching / record linkage pipeline** for matching business entities from a primary source (`S1`) against two candidate sources (`S2` and `S3`).

The pipeline combines:

1. Text normalization and standardization
2. Exploratory data analysis
3. Rule-based candidate generation / blocking
4. Feature engineering
5. Deep-learning based binary classification
6. Validation using **Macro F0.5**
7. Threshold selection
8. Test-set inference
9. Final submission formatting

The goal is to identify which `S2` and/or `S3` records refer to the same real-world business as each `S1` record.

# Pipeline

## 1. Data Loading

The notebook loads the three training sources and the three test sources using pandas.

TSV files are read with:

```python
pd.read_csv(..., sep="\t")
```

The ground-truth file is used to construct positive source-candidate pairs for supervised learning.

---

## 2. Text Normalization

Business names, addresses and countries are normalized before matching.

The normalization process includes:

- converting text to lowercase
- Unicode normalization
- accent folding
- replacing `&` and `+` with `and`
- removing punctuation
- collapsing repeated spaces
- expanding common business abbreviations
- expanding country-specific address abbreviations
- removing legal suffixes from business names
- extracting numbers from addresses

Examples of business-name normalization include abbreviations such as:

```text
Ltd  -> Limited
Pvt  -> Private
Corp -> Corporation
Co   -> Company
Inc  -> Incorporated
LLC  -> Limited Liability Company
```

A **core business name** is also generated by removing trailing legal-entity suffixes.

This produces fields such as:

```text
name_norm
name_core
name_ascii
address_norm
address_ascii
numeric_tokens
combined_norm
```

These normalized representations are used later for blocking and feature generation.

---

# 3. Exploratory Data Analysis

The notebook performs several checks before model training.

These include:

- source dataset sizes
- missing-value analysis
- address statistics
- duplicate address analysis
- common address tokens
- match-count distribution
- S2 vs S3 true-match distribution
- exact agreement between true matches
- approximate name/address similarity
- S1 matching patterns

The ground truth is also converted into individual positive pairs.

For example:

```text
S1-001 -> S2-103,S3-778
```

becomes:

```text
S1-001,S2-103
S1-001,S3-778
```

This makes the data suitable for pairwise binary classification.

---

# 4. Candidate Generation / Blocking

Comparing every S1 entity against every S2/S3 entity would create a very large number of pairs.

Instead, the pipeline uses **blocking** to generate a small set of plausible candidates.

Six blocking rules are used:

| Rule | Blocking Keys | Weight |
|---|---|---:|
| Exact core name | Country + core name | 5 |
| Exact ASCII name | Country + ASCII name | 4 |
| Exact address | Country + address | 5 |
| Name + number | Country + first 6 name characters + first number | 4 |
| Name + address prefix | Country + first 4 name characters + first 10 address characters | 3 |
| Name + numeric tokens | Country + first 4 name characters + numeric tokens | 4 |

Only sufficiently small buckets are considered.

Current configuration:

```python
MAX_BUCKET_SIZE = 20
MAX_CANDIDATES_PER_SOURCE = 12
```

The blocking stage also processes Source 1 in chunks to reduce memory usage.

Output:

```text
cheap_candidates.csv
```

---

# 5. Candidate Feature Engineering

After candidate pairs are generated, detailed pairwise features are calculated.

The model uses:

```text
rule_exact_core_name
rule_exact_ascii_name
rule_exact_address
rule_name6_number
rule_name4_address10
rule_name4_numeric
methods_found
block_score
numeric_exact
combined_exact
name_length_similarity
address_length_similarity
```

### Feature groups

#### Blocking features

These indicate which blocking rules retrieved the candidate.

#### Exact-match features

Examples:

```text
numeric_exact
combined_exact
```

#### Length similarity

The notebook calculates a normalized length similarity between the two strings:

```text
min(length_a, length_b) / max(length_a, length_b)
```

This provides a lightweight measure of structural similarity.

The final feature matrix is stored in:

```text
candidate_pairs_training_features.csv
```

and, for test data:

```text
test_model_features.csv
```


# 7. Deep Learning Model

The matching model is a fully connected neural network implemented using PyTorch.

Architecture:

```text
Input
  ↓
Linear(input_size → 128)
  ↓
BatchNorm
  ↓
GELU
  ↓
Dropout(0.25)
  ↓
Linear(128 → 64)
  ↓
BatchNorm
  ↓
GELU
  ↓
Dropout(0.20)
  ↓
Linear(64 → 32)
  ↓
BatchNorm
  ↓
GELU
  ↓
Dropout(0.15)
  ↓
Linear(32 → 16)
  ↓
GELU
  ↓
Dropout(0.10)
  ↓
Linear(16 → 1)
```

The output is a single logit representing the probability that a candidate pair is a true entity match.

The model is trained with:

```python
BCEWithLogitsLoss
```

and optimized using:

```python
AdamW
```

Gradient clipping is also used during training.

---

# 8. Validation and Threshold Selection

The notebook creates a deterministic validation split using a hash of:

```text
source1_entity_id
```

The validation bucket is controlled by:

```python
VAL_MOD = 20
VAL_BUCKET = 0
```

The validation metric is **Macro F0.5**.

F0.5 gives more importance to precision than recall, which is useful when false positive entity matches are costly.

The notebook evaluates multiple probability thresholds and selects the threshold producing the highest validation Macro F0.5.

The selected threshold is saved inside the model checkpoint.

---

---

# 11. Final Submission Formatting

The final notebook section converts pairwise predictions into one row per Source 1 entity.

Output:

```text
output/matching_results_formatted.tsv
```

Format:

```text
source1_entity_id    matched_entity_ids
```

Example:

```text
S1-001    S2-103,S3-778
S1-002
S1-003    S2-921
```

If an S1 entity has no predicted match, the `matched_entity_ids` field is left empty.

The final output contains all Source 1 entities, including entities for which the model predicts no match.

# Summary

This solution uses a two-stage entity-matching strategy:

### Stage 1 — Candidate Retrieval

Rule-based blocking reduces the enormous search space by retrieving only plausible S2/S3 candidates for each S1 entity.

### Stage 2 — Candidate Classification

A PyTorch neural network evaluates engineered pairwise features and predicts whether each candidate pair represents the same real-world entity.

The final system therefore combines:

```text
Normalization
     +
Blocking
     +
Feature Engineering
     +
Deep Learning
     +
Threshold Optimization
     =
Entity Matching
```

This design reduces computational cost while retaining multiple matching signals for difficult business-name and address variations.
